1 The Core Idea — What Are We Actually Doing?

The Employee Analogy Imagine you hire a new employee. After watching them work for 6 months, you know: "When it's busy and hot outside, they process about 80 orders per hour." One day you check — it's busy, it's hot — but they only processed 40 orders. Something is wrong. You didn't need to know why. You just knew it was abnormal compared to what you expected under those conditions.

That is exactly what this system does for wind turbines.

The User Story

As a wind farm engineer, I want to be alerted when a turbine is behaving abnormally compared to what it should be doing under its current operating conditions, so that I can investigate before a costly breakdown occurs.

The Core Technical Idea in Plain English

The system does not detect faults by looking for high temperatures or strange vibrations directly. Instead it:

  1. Learns what sensor values are normal for a given set of operating conditions (wind, load, RPM, temperature).
  2. At any new moment, predicts what the sensor value should be.
  3. Compares the actual reading to the predicted reading.
  4. A large gap = something unusual is happening.

This approach is called a Normal Behaviour Model (NBM). You are not classifying failures — you are detecting deviations from learned normality.

Why not just say "above 80 degrees = fault"? Because 80 degrees might be perfectly normal when the turbine is running at full power on a hot day. And 65 degrees might be abnormal when the turbine is barely running. Fixed thresholds ignore operating context. The NBM approach accounts for it.

5 Step-by-Step: How Phase 4 Works

Step 1 — Teach the Model What Normal Looks Like

User Story: As the system, I want to learn "given these operating conditions, what should the gearbox temperature be?" by studying only the periods when everything was fine.

You show the model thousands of 10-minute snapshots from healthy turbine operation. For each snapshot you tell it:

"Wind speed = 8.3 m/s, Power output = 1,200 kW, Generator RPM = 1,450, Ambient temp = 14 degrees, Pitch angle = 7 degrees... and the gearbox bearing temperature was 64 degrees."

The model learns the statistical relationship: operating conditions → expected sensor readings.

Inputs to the Model (Conditioning Variables)

These describe how the turbine is working right now. They set the context, not health status.

Step 2 — Calculate the Surprise (Residuals)

User Story: As the system, I want to calculate how far the actual sensor reading is from what I expected, so I can measure how "surprised" I am.
Residual = Actual Reading - Expected Reading

Example — Gearbox Bearing Temperature:

Model predicted: 64 degrees C (based on wind = 8.3 m/s, RPM = 1,450, etc.) Actual measured: 72 degrees C Residual = 72 - 64 = +8 degrees C "8 degrees hotter than it should be!"
Residual valueInterpretation
Large positive (+)Hotter / higher than expected — potential fault signal
Large negative (-)Colder / lower than expected — also worth investigating
Near zeroBehaving exactly as expected — normal

Step 3 — Make Residuals Comparable (Z-Score Standardisation)

User Story: As the system, I want to compare gearbox temperature residuals with hydraulic pressure residuals fairly, even though one is in degrees C and the other is in bar.

The problem: A gearbox residual of +8 degrees C and a hydraulic residual of +0.5 bar cannot be directly compared — completely different scales.

The solution — Z-score standardisation:

Z-score = (Residual - Mean of training residuals) / (Std Dev of training residuals)
Z-score rangeInterpretation
0.0 – 1.0 sigmaEssentially normal behaviour
1.0 – 2.0 sigmaSlightly elevated — monitor
2.0 – 3.0 sigmaNoticeably abnormal
Greater than 3.0 sigmaStrongly abnormal — likely anomaly
Critical rule: The mean and standard deviation must be calculated only from the training fold — the healthy historical data before the test event. Never from the full dataset. Using test-event data for this calculation is data leakage.

Step 4 — Group by Component (Component Scores)

User Story: As the system, I want to know if the GEARBOX is suspicious as a whole, not just one sensor inside it.

Instead of showing 20+ individual Z-scores, you group related sensors by subsystem and produce one score per component:

Gearbox Component Score |- dT_gbx_brg z-score -> +3.1 sigma |- dT_gbx_oil z-score -> +2.8 sigma `- gbx_brg_minus_oil -> +1.2 sigma ------------------------------------------- Gearbox Score -> aggregation of above (e.g. median = 2.8 sigma)

Step 5 — One Score per Event (Event-Level Aggregation)

User Story: As the system, I want ONE anomaly score for each event — not one per 10-minute reading — because a single bad reading doesn't mean the turbine is broken.

An event window may contain hundreds of 10-minute readings. You must summarise them into one score. You test three methods:

StrategyFormulaWhat it capturesBest for
A — Median Middle value of all Z-scores Typical behaviour across the whole event Robust; ignores isolated spikes
B — 95th Percentile Top 5% of Z-scores Captures the worst excursions Faults with strong but brief spikes
C — Persistence % of readings above threshold How consistently abnormal the event was Faults that are sustained, not sudden

The best strategy is chosen by experiment, not by assumption.

Step 6 — Decide: Normal or Anomaly? (Thresholding)

User Story: As the system, I want a cut-off score — above which I call the event anomalous.
If event_score > threshold → ANOMALY If event_score ≤ threshold → NORMAL
Critical rule for threshold selection: The threshold must be chosen using normal/control events only. You must never look at the known anomaly events to select it. Doing so is like looking at the exam answers beforehand — results look good but are scientifically invalid.

Step 7 — Which Component Caused It? (Explainability / XAI)

User Story: As a wind farm engineer, I want to know not just THAT something is wrong, but WHICH part of the turbine is responsible, so I know what to inspect.

The system produces three levels of explanation:

Level 1 — Component Attribution

Event 51 — ANOMALY DETECTED Component scores: Gearbox +3.2 sigma [===========] <- Main culprit Generator +0.5 sigma [==] Hydraulic +0.4 sigma [=] Transformer +0.1 sigma [|] Conclusion: Investigate the gearbox.

Level 2 — Ridge Coefficients (Ridge model only)

For the Ridge model, you can see exactly which operating conditions influence each sensor prediction:

Gearbox bearing temp — Ridge coefficients: Power output +0.65 (strong positive driver) Generator RPM +0.21 Ambient temp +0.14 Wind speed +0.08

Level 3 — SHAP Values (for Random Forest and XGBoost)

SHAP values show how each input feature pushed the model's prediction up or down for a specific observation. Applied at component group level — not as a 226-feature dump.

6 The Four Models — Who Does the Predicting?

All four models do the same job: given the operating conditions, predict the expected sensor value. They just do it differently.

ModelSimple analogyStrengthsWeaknesses
Ridge Regression (Primary) A very smart ruler. Finds the best straight line through your data. Simple and interpretable. Coefficients show exactly which condition drives the prediction. Cannot capture complex "if A and B together, then..." interactions.
Decision Tree (Baseline) A flowchart. "If wind greater than 10 m/s go left. If RPM greater than 1,200 go right..." Very interpretable. Engineers can follow the logic step by step. Tends to overfit — memorises training data too specifically.
Random Forest (Ensemble) You ask 100 independent experts, each seeing slightly different data, and average their answers. Much more robust than a single tree. Handles noisy sensor data well. Harder to interpret than Ridge. Slower to train.
XGBoost (Advanced) Each new expert learns from the mistakes of the previous expert. Iterative improvement. Often state-of-the-art accuracy on tabular data. Black-box by nature; requires SHAP for explanation.
You do NOT assume XGBoost is best. The whole point of running all four is to experimentally determine which model produces the most useful residuals for this specific dataset. The result comes from the data, not from assumptions.

7 Leakage — The Biggest Beginner Mistake

Data leakage means accidentally letting the model see information it should not have at prediction time. It produces results that look great in testing but fail in the real world. There are three types to prevent.

Type 1 — Temporal Leakage

The Exam Analogy: Temporal leakage is like training a student on next year's exam paper before they sit this year's exam. Results look perfect but prove nothing.
Wrong (leakage)Correct
Random 80/20 split of the 425,023 rows Training uses only data with timestamps strictly before the test event
Fitting a global scaler on all data including the test event Scaler fitted on training fold only; applied to test fold
Using forward-looking rolling windows Only backward-looking rolling windows (Phase 3 already does this correctly)
Correct timeline: Past ---[TRAIN: normal data strictly before event]---[TEST EVENT]--- Future ↑ ↑ Learn from here Evaluate here (all normal data before) (never seen in training)

Type 2 — Turbine Leakage

The Department Analogy: Turbine leakage is like using data from Department B to study Department A. Each turbine has its own mechanical characteristics and cannot share a model.
A0's model = trained on A0's normal historical data only A10's model = trained on A10's normal historical data only A11's model = trained on A11's normal historical data only A13's model = trained on A13's normal historical data only A21's model = trained on A21's normal historical data only

Type 3 — Label Leakage

Wrong (leakage)Correct
Including status_type_id, event_id, or any fault label as model input Model sees operating conditions only; labels used offline to filter training data
Threshold chosen by looking at anomaly event scores Threshold chosen using normal/control events only

8 How You Measure Success

The evaluation unit is ONE EVENT, not one SCADA row. You have 21 independent events — that is your effective sample size for evaluation. Do not report metrics over 425,023 rows. They are misleading because consecutive 10-minute readings are correlated and not independent.

Primary Metrics

MetricFormulaPlain English
Detection Rate (DR) TP / (TP + FN) Out of 11 real anomaly events, how many did we catch?
False Alarm Rate (FAR) FP / (FP + TN) Out of 10 normal events, how many did we wrongly flag?
ROC-AUC Area under ROC curve Overall ability to separate anomaly from normal across all thresholds
PR-AUC Area under Precision-Recall curve Performance when positives (fault events) are the minority class

Confidence Intervals Are Mandatory

With only 21 events, one event equals approximately 5% of your result. You must always report uncertainty:

Detection Rate = 72.7% [95% CI: 43.4% - 90.3%] <- Correct Detection Rate = 72.7% <- WRONG — misleadingly precise

Use Clopper-Pearson exact binomial confidence intervals.

Metrics NOT to Use as Primary Evidence

MetricWhy it is invalid here
Observation-level accuracy over 425,023 rowsCorrelated rows inflate accuracy; does not reflect event-level performance
Observation-level F1Same problem as above
Average lead timeNot supported — most faults have no pre-event normal observations
Per-failure-mode accuracyMany failure modes have n=1 or n=2 examples — not statistically meaningful

9 The Validation Framework (LOEO-CV)

LOEO = Leave-One-Event-Out Cross-Validation. You have 21 events, so you run 21 rounds:

Round 1: Hold out Event_01 as TEST. Train on normal data before Event_01. Round 2: Hold out Event_02 as TEST. Train on normal data before Event_02. Round 3: Hold out Event_03 as TEST. Train on normal data before Event_03. ... Round 21: Hold out Event_21 as TEST. Train on normal data before Event_21. Every event gets evaluated exactly once. No event ever influences its own model training or standardisation.
This is the most important design decision in the entire project. It is what makes the results scientifically valid and defensible in front of your jury.

12 Implementation Steps

Execute in this order. Inspect output after each step before proceeding.

  1. Feature inventory: Load engineered_features.parquet. Confirm 425,023 rows x 226 columns. Verify all conditioning and target variables exist.
  2. Define inputs and targets: Produce selected_features.csv and feature_groups.csv mapping each sensor to its component group.
  3. Build 21 LOEO folds: For each event, define its training set (same turbine, normal status, timestamp before event start). Save to loeo_event_folds.csv.
  4. Implement Ridge NBM: Train one Ridge model per target per turbine per fold. Save models and coefficients.
  5. Validate Ridge residuals: Plot actual vs. expected for representative sensors. Confirm residuals are centred near zero during normal periods.
  6. Implement Decision Tree NBM: Same pipeline structure as Ridge. Save models.
  7. Implement Random Forest NBM: Same pipeline structure. Save models.
  8. Implement XGBoost NBM: Same pipeline structure. Save models.
  9. Standardise residuals: For each fold, compute mean and std from training residuals only. Apply Z-score. Never use test-event statistics.
  10. Apply 3 aggregation strategies: Median, 95th percentile, and Persistence — for all model/component/event combinations.
  11. Run full LOEO-CV: Execute all 12 experiment combinations (4 models x 3 aggregations) across all 21 folds.
  12. Event-level evaluation: Compute DR, FAR, ROC-AUC, PR-AUC, Precision, Recall, F1 with Clopper-Pearson confidence intervals over the 21 events.
  13. Ablation study: Repeat with gearbox-only, generator-only, and hydraulic-only feature sets to measure individual component contribution.
  14. XAI: Generate component attribution tables, Ridge coefficient plots, and SHAP analyses for RF and XGBoost.
  15. Final comparison: Populate the results table. Select the best model and aggregation based on evidence. Write conclusions.

13 The One Sentence for Your Jury

When your jury asks "What is your methodology?"

"We model the expected normal behaviour of wind-turbine components under their operating conditions, calculate actual-versus-expected residuals as health indicators, aggregate these deviations into event-level anomaly scores, compare multiple NBM algorithms under leakage-controlled leave-one-event-out validation, and provide component-level explanations of detected anomalies."

The Five-Point Summary

  1. Learn normal: Train models on healthy turbine data to predict expected sensor values under current operating conditions.
  2. Measure surprise: Residual = Actual minus Expected. This is the health signal.
  3. Standardise: Convert residuals to Z-scores so components on different scales can be compared fairly.
  4. Aggregate per event: Summarise the window of Z-scores into one event-level score using Median, P95, or Persistence.
  5. Evaluate fairly: Leave-one-event-out CV; report Detection Rate, FAR, and AUC with Clopper-Pearson confidence intervals over 21 independent events.
